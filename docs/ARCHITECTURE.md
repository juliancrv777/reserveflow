# Architecture decision record

## 001 — A modular service with one database

**Status:** accepted for version 1.

**Context:** the core failure modes are overselling, duplicate reservations and partial writes. They can be demonstrated without a distributed system.

**Decision:** keep one HTTP process with explicit HTTP, domain and persistence modules. Use Node.js 24's built-in SQLite integration and test runner. There are no third-party runtime dependencies. SQL values always use bound parameters.

**Consequence:** cloning and running the demo needs only Node.js. A small native HTTP boundary makes request validation, body limits and error mapping visible. The tradeoff is maintaining those concerns ourselves; a framework becomes worthwhile as the API surface grows. JavaScript keeps setup small, but a future TypeScript migration would add compile-time checks as the model expands.

## 002 — Conditional inventory updates inside a transaction

**Invariant:** `available + sum(confirmed reservation quantities) = capacity` for each event.

The database also enforces `0 <= available <= capacity`. The sum invariant is maintained by reservation and cancellation transactions; it is not enforced by a cross-table SQL constraint.

Reservation sequence:

1. Start `BEGIN IMMEDIATE`, acquiring the write transaction before reading state.
2. Look up `(principal_id, idempotency_key)`.
3. If present, compare the fingerprint and return the saved response or a conflict.
4. Check event existence for a useful 404 response.
5. Execute `UPDATE events SET available = available - ? WHERE id = ? AND available >= ?`.
6. If no row changed, return `SOLD_OUT` and roll back.
7. Insert the reservation, saved response and audit record.
8. Commit; only then send the success response.

The conditional write protects inventory at the database boundary. A read-then-write check without transaction protection could allow two processes to observe the same availability. Worker-thread tests use distinct connections to test contention beyond a single Node event loop.

If the process loses the response after commit, the client can retry the same key. If any database operation fails before commit, all changes roll back. An injected audit failure tests this exact boundary.

## 003 — Idempotency is a durable operation result

Keys belong to a principal, not globally to every customer. The fingerprint hashes a canonical array of the two business inputs, so JSON property order does not change identity. Unknown input fields are ignored. Reusing a key with another event or quantity returns 409.

Successful operation results are retained indefinitely in this version. Invalid and sold-out requests do not reserve a key. A retry after cancellation still receives the creation result; a GET returns the current status. This preserves operation identity across state changes. A new booking needs a new key.

There is no exactly-once network delivery claim. The guarantee is one committed reservation for one successful `(principal, key)` pair while the record is retained.

## 004 — Authentication for service clients

The operator provisions cryptographically random 256-bit API tokens. Only SHA-256 token hashes are stored. Fast hashing is appropriate here because the input is a high-entropy machine token, not a human password. Each key creates a principal with an admin or customer role.

Admin keys can create events and read the audit trail. Reservation reads and cancellations are owner-only even for admins. Foreign reservations return 404. No tokens or request bodies are included in request logs. HTTP response IDs are generated by the server.

Tradeoff: there is no interactive login, revocation UI or credential lifecycle yet. Losing a key loses normal API access to that principal. Do not use this model for a public end-user product without evolving credential management.

## 005 — SQLite is a bounded deployment choice

WAL permits readers while a writer works, but SQLite still has one writer at a time. Each connection waits up to five seconds for locks. The synchronous driver blocks its event loop while waiting, so this design does not claim high concurrency throughput.

The schema version and initial migration are committed together. Future migrations must be sequential, tested on existing data and backed up before operation.

Move to PostgreSQL when measured contention or multiple application hosts justify it. Preserve the conditional update and idempotency uniqueness, and test isolation again using real concurrent PostgreSQL connections. Redis alone would not replace the database invariant.
